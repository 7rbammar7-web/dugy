# خطة المرحلة الثانية: التشفير الطرفي والخادم

> مسودة تصميم تحتاج إلى مراجعة الفريق الفني ثم مراجعة أمنية مستقلة. لم يُنفَّذ منها شيء بعد.

## 1. اختيار مكتبة البروتوكول

**المرشح الأول: libsignal** (Signal Protocol: X3DH/PQXDH + Double Ratchet).

- منشورة على Maven Central باسم `org.signal:libsignal-android`، وتعتمد على `org.signal:libsignal-client`.
- **الترخيص AGPLv3.** دمجها يُلزم بنشر شفرة التطبيق تحت ترخيص متوافق. يجب حسم ذلك قانونيًا قبل البدء.
- تقول Signal في توثيق المكتبة إنها تنشر الحزم «لاستخدامها الخاص» وإن الاستخدام خارج Signal غير مدعوم. لذلك يجب تثبيت إصدار محدد، ومتابعة التغييرات التي تكسر التوافق بين الإصدارات.

**بدائل للتقييم:** مثل vodozemac، وهو تنفيذ Olm/Megolm بلغة Rust لمشروع Matrix. يُقيَّم بالمعايير نفسها: الصيانة، والمراجعات الأمنية، والترخيص، وسهولة الربط مع أندرويد.

**القاعدة:** لا تُكتب أي خوارزمية أو بروتوكول تشفير يدويًا. الملف `AesGcm.kt` الحالي مخصص للتخزين المحلي فقط.

## 2. المفاتيح والأجهزة

| العنصر | مكانه |
|---|---|
| مفتاح الهوية الخاص لكل جهاز | على الجهاز فقط، داخل مخزن البروتوكول المشفّر بمفتاح البيانات |
| Signed prekey وOne-time prekeys (وKyber prekeys إن اعتُمد PQXDH) | الجزء العام على الخادم، والخاص على الجهاز |
| الجلسات (Double Ratchet) | على الجهاز فقط |

- **كل جهاز له مفاتيحه الخاصة.** الرسالة تُشفَّر مرة لكل جهاز من أجهزة المستلم (fan-out).
- **إضافة جهاز:** بمسح QR من جهاز قائم. لا تُنسخ المفاتيح الخاصة إلى الخادم أبدًا.
- **فقدان جهاز:** يُلغى من قائمة الأجهزة، فيرى الطرف الآخر تحذير «تغيّرت أجهزة جهة الاتصال».
- **التحقق:** يُعرض رمز أمان رقمي ورمز QR من بصمتي مفتاحي الهوية (توفر libsignal مولّد بصمات). يُحفظ المفتاح الموثّق، وعند تغيّره يظهر تحذير واضح، ولا تُرسل الرسائل الجديدة إلا بعد إقرار المستخدم بالتحذير.

## 3. الخادم (مثال: Firebase)

### الهوية

حسابات Firebase Authentication. يُفضَّل التعارف برموز دعوة بدل أرقام الهواتف لتقليل البيانات المجمّعة.

### نموذج البيانات (Firestore)

```
users/{uid}                         { createdAt }                     — بلا اسم حقيقي إلزامي
users/{uid}/devices/{deviceId}      { identityKeyPub, registrationId, signedPreKey, lastSeenDay }
prekeys/{uid}/devices/{deviceId}/oneTime/{keyId}   { pub }           — تُستهلك مرة واحدة
mailboxes/{rcptUid}/devices/{deviceId}/envelopes/{envelopeId}
                                    { ct, type, senderDevice, createdAt, expireAt }
```

- `ct` هو النص المشفّر بصيغة base64. لا يُخزَّن أي نص صريح أو مفتاح خاص.
- `expireAt` حقل TTL. تحذف سياسة TTL في Firestore المستندات المنتهية تلقائيًا دون اعتماد على فتح التطبيق. الحذف ليس فوريًا وقد يتأخر عادةً حتى 24 ساعة، وتبقى المستندات المنتهية ظاهرة في الاستعلامات إلى أن تُحذف، لذلك يتجاهل العميل أي مستند تجاوز `expireAt`.
- يحذف جهاز المستلم المغلّف من الخادم فور فك تشفيره بنجاح.
- **استهلاك one-time prekey** يجب أن يكون ذريًّا (Cloud Function أو transaction) حتى لا يُستخدم المفتاح مرتين.

### قواعد الأمان (مسودة غير مختبرة)

```
rules_version = '2';
service cloud.firestore {
  match /databases/{db}/documents {
    match /users/{uid} {
      allow read: if request.auth != null;
      allow write: if request.auth.uid == uid;
      match /devices/{deviceId} {
        allow read: if request.auth != null;
        allow write: if request.auth.uid == uid;
      }
    }
    match /prekeys/{uid}/devices/{deviceId}/oneTime/{keyId} {
      allow create, delete: if request.auth.uid == uid;
      allow read, update: if false;   // الاستهلاك عبر Cloud Function فقط
    }
    match /mailboxes/{rcpt}/devices/{deviceId}/envelopes/{id} {
      allow create: if request.auth != null
        && request.resource.data.keys().hasOnly(['ct','type','senderDevice','createdAt','expireAt'])
        && request.resource.data.ct is string
        && request.resource.data.ct.size() < 131072;
      allow read, delete: if request.auth.uid == rcpt;
      allow update: if false;
    }
  }
}
```

قواعد الأمان تمنع المستخدمين من قراءة بيانات غيرهم، لكنها **ليست بديلًا عن التشفير الطرفي**.

### الإشعارات

رسالة FCM من نوع data، بلا محتوى ولا اسم مرسل، وظيفتها إيقاظ التطبيق فقط. بعدها يجلب التطبيق المغلّفات ويفك تشفيرها، ثم يعرض الإشعار المحلي وفق إعداد المستخدم (`Notifier`).

## 4. البيانات الوصفية التي سيراها مزود الخدمة

| البيان | يراه Firebase/Google؟ | ملاحظة |
|---|---|---|
| نص الرسالة | لا | مشفّر طرفيًا |
| مفاتيح فك التشفير | لا | على الأجهزة فقط |
| معرّف المستلم (uid) | نعم | ضروري للتوجيه |
| هوية المرسل | نعم ضمنيًا | الطلب موقّع بحساب المرسل حتى لو لم يُخزَّن الحقل. إخفاؤها (sealed sender) يحتاج بنية مختلفة |
| التوقيت وحجم المغلّف | نعم | يمكن حشو الرسائل (padding) لتقليل كشف الحجم |
| عنوان IP وبيانات الجهاز | نعم في سجلات المنصة | يُذكر في سياسة الخصوصية |
| رموز FCM | نعم | لا تحمل محتوى |

## 5. التغييرات في التطبيق

1. إضافة `android.permission.INTERNET`.
2. تنفيذ `SignalTransport : MessageTransport` بالشروط الموثّقة في الواجهة: تشفير قبل الشبكة، وعدم تكرار الإرسال باستخدام `messageId`.
3. مخزن بروتوكول (identity, prekeys, sessions) داخل ملف مشفّر بمفتاح البيانات نفسه.
4. شاشة رمز الأمان وQR، وتحذير تغيّر المفتاح، وقائمة الأجهزة.
5. مؤقت الرسائل المؤقتة داخل الرسالة المشفّرة نفسها حتى يطبّقه الطرفان، و`expireAt` على الخادم.
6. «حذف للطرفين» برسالة تحكم مشفّرة، مع توضيح أنه لا يضمن الحذف من جهاز الطرف الآخر.
7. اختبار الإرسال والاستقبال على جهازين حقيقيين، ثم مراجعة أمنية مستقلة قبل أي ادعاء أمني أو إطلاق.
